# disco_bot

Discord-бот с ИИ для админов игрового сервера. Читает тикеты игроков, ищет похожие
кейсы с уже принятыми решениями, ходит в логи сервера и выдаёт админу разбор с
рекомендацией. База кейсов пополняется решениями админов и со временем становится
живым регламентом.

## Что делает

1. **Читает тикеты.** Новый тикет (сообщение/тред в канале тикетов) → бот извлекает
   суть жалобы, ник/ID игрока, время, тип (чит, баг, потеря лута, спор, бан-апелляция…).
2. **Ищет похожие кейсы.** По базе решённых тикетов: семантический поиск + фильтры
   (тип, игрок, период). Показывает 3–5 похожих случаев и что по ним решили.
3. **Ходит в логи.** По контексту тикета (игрок, время ±N минут, тип события) достаёт
   фрагменты логов сервера и пишет вывод фактами, без домыслов.
4. **Даёт совет админу.** В админском треде: суть → факты из логов → похожие кейсы →
   рекомендация → уверенность. Админ принимает решение командой `/resolve`, кейс с
   решением уходит в базу — база учится.

## Архитектура

```
app/
  bot/          discord.py: слушатели каналов тикетов, слэш-команды (/analyze, /similar,
                /resolve, /case), вывод в админский тред
  cases/        база кейсов: SQLite (cases, decisions, embeddings), поиск похожих
                (эмбеддинги + FTS5 фолбэк), импорт истории
  logs/         адаптеры логов: интерфейс LogSource (local file / SFTP / API),
                парсеры форматов, запросы «игрок + окно времени + тип события»
  ai/           Claude API (SDK `anthropic`, модель claude-opus-5): извлечение полей
                тикета, разбор логов, итоговая рекомендация — структурированный вывод
  web/          (позже) FastAPI: просмотр базы кейсов и логов, как в test_hub
tests/
```

Принципы:
- **ИИ не выдумывает.** Факты только из логов и кейсов; если данных нет — так и пишет.
- **Обучение = накопление кейсов**, не дообучение модели. Каждое решение админа — запись.
- **Логи через адаптер.** Источник логов (файл, SFTP, панель хостинга) меняется без
  правки остального кода.
- Эмбеддинги — локальная модель (`sentence-transformers`, мультиязычная), чтобы поиск
  похожих не стоил токенов; Claude вызывается только на разбор.
- Секреты в `.env` (см. `.env.example`), в git не попадают.

## Запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env   # заполнить переменные, см. ниже
.venv/bin/python -m app.bot
```

Тесты: `.venv/bin/pytest -q`.

### Переменные окружения (`.env`)

Обязательно заполнить:

- `DISCORD_TOKEN` — токен бота (как получить — см. ниже).
- `DISCORD_GUILD_ID` — ID сервера (гильдии), на который приглашён бот; используется
  для мгновенной синхронизации слэш-команд на этом сервере.
- `DISCORD_TICKET_CHANNEL_IDS` — ID канала(ов) с тикетами игроков, через запятую.
  Сообщения в этих каналах (и тредах внутри них) бот разбирает автоматически.
- `DISCORD_ADMIN_CHANNEL_ID` — ID канала/треда, куда бот публикует разборы для админов.
- `ANTHROPIC_API_KEY` — ключ Claude API.
- `CLAUDE_MODEL` — модель Claude для разбора (по умолчанию `claude-opus-5`).
- `DB_PATH` — путь к файлу SQLite с базой кейсов (по умолчанию `data/disco_bot.db`).

Остальные переменные (`LOG_SOURCE`, `LOG_DIR`) относятся к миссии 2 (логи) и пока
не обязательны.

### Как получить DISCORD_TOKEN

1. Открыть [Discord Developer Portal](https://discord.com/developers/applications) →
   **New Application** → задать имя.
2. Перейти на вкладку **Bot** → **Reset Token** / **Copy** — это и есть `DISCORD_TOKEN`.
3. На той же вкладке **Bot** включить привилегированный интент
   **Message Content Intent** — без него бот не получит текст сообщений в каналах
   тикетов и не сможет их разобрать.
4. Пригласить бота на сервер: вкладка **OAuth2 → URL Generator**, выбрать scopes
   `bot` и `application.commands` (последний нужен для слэш-команд), из прав бота —
   как минимум чтение сообщений (View Channels, Read Message History), отправка
   сообщений (Send Messages), создание тредов (Create Public Threads) и Embed Links.
   По сгенерированной ссылке авторизовать бота на нужном сервере.

### Команды бота

Слэш-команды (`app/bot/client.py`):

- `/analyze message` — разбор тикета по ссылке на сообщение Discord или его ID
  (ищет сообщение в текущем канале и в каналах из `DISCORD_TICKET_CHANNEL_IDS`).
  Создаёт/обновляет кейс, извлекает суть через Claude, ищет похожие кейсы, публикует
  разбор в тред админского канала.
- `/similar text k` — поиск похожих кейсов по произвольному тексту без вызова Claude
  (`k` — сколько кейсов показать, по умолчанию 5).
- `/resolve case_id decision` — фиксирует решение админа по кейсу (текст решения).
- `/case case_id` — карточка кейса: текст тикета, игрок, категория, решение (если есть).

Кроме слэш-команд, бот сам разбирает каждое новое сообщение в каналах из
`DISCORD_TICKET_CHANNEL_IDS` (без вызова команды) и публикует разбор в админский тред.

## Логи

Ядро миссии 2 готово и работает end-to-end на фикстурах (`tests/fixtures/logs/`,
`tests/test_logs_*.py`). Полная спецификация форматов логов (ADM, server_console,
LBmaster, ZF, CarCodeLock), координат и идентичности игрока, а также разборы реальных
кейсов владельца — в `docs/LOGS.md`; здесь только про то, как разложить выгрузку и
запустить индексацию.

### Куда положить выгрузку владельца

Разложить архивы в `LOG_DIR` — `ingest` обходит каталог рекурсивно и распознаёт файлы
по имени, а не по имени родительской папки, но рекомендуемая раскладка (как в архивах
владельца, см. `docs/LOGS.md`):

- `log_storage/<unix_ts>/*.ADM`, `server_console.log`, `LBmaster_*.log` — своя папка
  `<unix_ts>` на каждую игровую сессию (рестарт раз в 4 часа).
- `_ZFServerLog/zfbubusik_log-[DD-MM-YYYY] - HH;MM;SS.log`
- `Logs/CarCodeLock_YYYY-MM-DD_HH-MM.log`

`.rar`/`.zip` на пути можно не распаковывать — `ingest` сам распаковывает их через
`bsdtar` (должен быть установлен и быть в `PATH`) во временную директорию.

Важно: в строках `server_console.log` даты нет — она берётся из имени папки сессии
(`<unix_ts>`), поэтому эти файлы должны лежать именно внутри такой папки, иначе
индексатор возьмёт текущую дату. `*.ADM` и `LBmaster_*.log` дату берут из заголовка/имени
файла и от вложенности не зависят.

### Переменные окружения

Уже заведены в `.env.example`:

- `LOG_SOURCE` — источник логов (сейчас только `local`).
- `LOG_DIR` — где лежит выгрузка; путь в индексатор передаётся явно аргументом команды
  `ingest` (см. ниже), из env он не читается автоматически.
- `LOG_DB_PATH` — путь к SQLite-индексу логов (`app/logs/index.py`), по умолчанию
  `data/logs.db`.

Не заведена в `.env.example`, но читается кодом:

- `SERVER_TZ` — часовой пояс сервера (по умолчанию `Europe/Moscow`), только для справки
  в `app/logs/facts.py`. Все `ts` в индексе и в окнах `since`/`until` — naive local time,
  без привязки к UTC; конвертации по `SERVER_TZ` нет (см. соглашение о времени в
  `docs/LOGS.md`).

### CLI (`python -m app.logs`)

```bash
.venv/bin/python -m app.logs ingest "$LOG_DIR"
# файлов разобрано: 5, пропущено (не изменились): 0, событий записано: 812

.venv/bin/python -m app.logs player Kazah --since 2026-11-09T00:00:00
# known names=['Kazah'] steam64s=['76561198...']
# 2026-11-09T04:07:12 [connect] Kazah: ...
# всего событий: N

.venv/bin/python -m app.logs vehicle Bastard_cj7_green
# 2026-11-09T04:10:00 [vehicle_open] ...
# всего событий: N

.venv/bin/python -m app.logs container BRDK_PersonalChest_Blue --since 2026-11-09T00:00:00
# 2026-11-09T04:12:00 [item_action] dimonbigboy: ... положил ...
# всего событий: N; брали/класли: dimonbigboy

.venv/bin/python -m app.logs near 8090.1 9330.9 50 --at 2026-11-09T04:07:00 --window 10
# Nomad (76561198...) — 12.3 м, 2026-11-09T04:05:00
# всего игроков рядом: N
```

`ingest` инкрементальный: файл с тем же размером и mtime, что уже записан в таблицу
`files`, парсится заново только если что-то изменилось. `player` принимает ник,
steam64 или BI-hash — одного и того же игрока сводит резолвер идентичностей
(`app/logs/identity.py`) по таблице `identities`, которая наполняется коннектами из
ADM/console/LBmaster. `container` ищет, кто брал/клал предметы в контейнер или машину
заданного класса (ZF `item_action`/`container_move`, в том числе действия ботов —
`extra['actor_class']`), по корню цепочки контейнеров (`src_root_class`/`dst_root_class`,
подробности в `docs/LOGS.md`), а не по подстроке во всей цепочке.

### Что не индексируется

IP-адрес игрока и `RConPassword` из `server_console.log` в индекс не попадают —
парсер (`app/logs/console.py`) намеренно не кладёт их ни в одно поле события, из
соображений приватности и безопасности (подробнее — `docs/LOGS.md`, раздел про
`server_console.log`). Сами файлы выгрузки в git не кладутся.
